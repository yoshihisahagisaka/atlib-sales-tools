# 04 Report Contract・最小差分・判断論点
提案版：PIRA-P-2.0.0 / 固定文版PIRA-N-2.0.0。診断結果の正本は以下の意味JSONと、同じ版の固定文から構成する6セクション。回答は自己申告であり、監査・認証・実態証明ではない。

## 結果Envelope
definitionId、answerContractVersion、answerRevision、ruleSetVersion、contentVersion、narrativeVersion、reportContractVersion、rendererVersion、inputHash、resultHash、renderedContentHash、reportRevisionを保持。sourceCodeShaは使用した将来実装のSHA。現在の設計サンプルはDESIGN_ONLYとし実装SHAを捏造しない。
意味JSONはstatus、businessIds、informationIds、currentStates（active質問順）、unknownQuestionIds、authorityQuestionIds、notApplicableQuestionIds、relevanceThemeIds、candidateThemeIds、priorityThemeIds、deferredThemeIds、themeEvidence、checklistIds、contentCardIds、nextActionIdsを含む。nextActionIdsは常にSELF_REVIEW,OPTIONAL_CONSULTATION,OPTIONAL_MEMBER_INVITATION。選択同意ではなく表示可能な案内のIDである。
各テーマはthemeId/sourceQuestionIds/sourceRuleIds/messageId/whatToVerify/whyUseful/expectedRecordを保持する。出典カードは前文書のmetadataをsnapshotへ取り込む。URL参照だけで本文を外部から動的取得しない。

## 6セクション契約
|固定key・見出し|入力・表示内容|0件・未確認時|禁止|
|---|---|---|---|
|S1 最近の事故・統計|固定S01/I01/I02、出典、公表日、件数の意味、固定版の注意|出典無効化時は新版で「参考情報更新中」、個別結果は維持|組合事故の予測、被害確率、最新と偽る|
|S2 組合の業務と重要情報|C01,C02の選択肢を定義順で表示。「ご回答では」を付ける|UNKNOWN/担当外をそのまま表示|公開調査や業務類型から旅券等の保有を自動認定|
|S3 現在の管理状況|全active回答の状態・対象。unknown/担当外/N/A別一覧。deferred件数とID・見出し|非表示業務質問は評価対象外と明示|READYを安全認定、N/Aを対策済みにする|
|S4 優先確認テーマ|0..3件、根拠質問、確認事項、目的、残す成果物。固定手順順|H01「今回の回答では追加の優先確認テーマはありません」。H02「未確認の項目があるため、今回の回答では優先確認テーマを選定していません」|必ず3件に水増し、危険度順、商品推薦|
|S5 実務チェックリスト|KSEL01で選ばれた本文。K02はopenな工程だけ。KUは未確認/担当外の実リスト付き|H01ならK00。未確認があればKUを付加|未回答の対策不足を仮定、確認事項を無制限列挙|
|S6 次の取り組み|自組合で資料を使う→必要なら相談→価値があれば企業へ任意案内。3選択肢は同列で任意|何も申し込まず結果保存可能|診断完了を営業登録・共同購買注文・PIRA共有同意と同一視|

状態表示の文型：READY＝「〔対象〕は、対象を決めて運用しているという回答です」。PARTIAL＝「〔対象〕は、一部で運用しているという回答です」。NOT_DONE＝「〔対象〕は、〔該当する確認/手順〕を実施・設定していないという回答です」。UNKNOWN＝「〔対象〕は、今回は分かりませんでした」。権限外＝「〔対象〕は、回答者の担当外で確認が必要です」。N/A＝「〔対象〕は、〔理由〕のため今回は対象外と回答しています」。
C07 NOT_DONEは「復元確認をしていない」、B01は「期限後の処理を決めていない」等、質問ごとの語句辞書を使う。NOT_DONEを「対策なし」の共通一語へ丸めない。

S4見出しは03文書のT名と完全一致。本文は「〔入力対象〕について、〔チェックリスト冒頭の作業〕を確認すると、現在の手順を続けるか見直すかの判断材料になります」。根拠は回答認識であり、事故統計は根拠questionIdsへ入れない。
S6固定文：「まず、今回の資料を事務局内や現在の委託先との確認にお使いください。追加の相談は任意です。資料が役立つと感じた場合は、所属企業にも自己点検の機会を案内できます。所属企業の回答や名簿を組合へ提出する必要はありません。商品購入や案内への協力は、結果を受け取る条件ではありません。」

## 再現・改訂・出力
1. active枝・整合検証後に回答snapshotを凍結する。
2. 複数選択を定義順へ正規化し、objectキーを整列してUTF-8 JSON化。既存contentHashの安定キー処理を候補として使用する。
3. inputHashは定義ID・回答契約版・正規化回答を対象。ルール/コンテンツ/文版/Report版を含むexecutionKeyとresultHashも保存する。時刻・UUIDは意味hashから除外。
4. 異なる版は別結果。旧版ルール・固定文・出典snapshotを保持して同じ版で再表示できる。
5. WebとPDFは同じ確定ReportContentを使用する。PDF生成時に再判定しない。表示中の回答が変わったら旧結果を現在の結果として表示しない。
6. PDFはネットワーク遮断・escape・timeout・同時実行制御・出典URLの印刷可読性を検証する。既存PDFサービスのAPPROVED条件を外す変更を既存IT経営経路に施さず、PIRA専用の確定snapshotアダプタから描画helperを使う。
7. フォント埋込と改頁・長文切れは実装後の視覚QA対象。今回のMarkdownサンプルはPDFの品質検証を意味しない。
8. 人間が文言を書き換えた場合は別reportRevision＋編集者/理由を保持し、自動出力との完全再現対象を分ける。本版の無料自己診断では都度の人手編集・承認は前提にしない。固定コンテンツの版公開時に人間が校閲する。

## 実装時の最小差分案（未実装）
推奨：ブラウザ内の無料自己点検を入口とし、既存確定診断と同じ「構造化入力→意味変換→確定ルール→固定文章」の処理方式にPIRA専用定義を追加する。公開の汎用ルールエンジン新設はしない。匿名回答を既存IT経営Caseへ作成しない。
- 新規のPIRA定義・schema・projection・bounded rule adapter・6章テンプレートに限定。既存Mルール/v2 analyzer/旧schemaは維持。
- 既存公開診断の質問操作、戻る/再回答、排他、escapeを適用できる単位で再利用する。sixAxis・スコア表示・confidence・自動サービス分岐は移植しない。
- 結果はダウンロード可能な版付きsnapshotとして返す。サーバ保存を選ばない初期案では閉じた後の復元は保存ファイルからのみ。後日の入力取込はschema/size/integrityを検証し、持込hashを証明と扱わない。
- 自動PDFを初期範囲に含めるなら、Salesの既存Playwright描画transportを分離利用するPIRA出力アダプタを追加。永続Caseを作る方式は別案。匿名PDFエンドポイントの濫用制御・入力上限・印刷資産・運用費は実装前に決定する。将来差分の量は概算せず境界合意後に見積もる。
- 無料相談は明示同意後にだけ連絡先と診断snapshotを送る。既存業務KAIZEN相談APIはdiagnosisDefinition/schemaが違うため無改造流用しない。PIRA用の型・同意文・受け側アダプタを用意する。
- 所属企業案内は回答を含まない共通案内文を手動取得できる。名簿収集や自動送信は実装範囲外。
- 共同購買PR14のproducer、application、formal orderへ自動接続しない。商品検討の明示操作は診断完了と別イベント。将来接続しても診断だけで商談/注文化しない。
- DBを必要とする継続利用へ拡張する場合、5層provenance思想を再利用し、PIRA独立定義/保存とする。IT経営FK・必須contactを無理に通すダミーデータは作らない。SQL/DDLはこのPRに含めない。
