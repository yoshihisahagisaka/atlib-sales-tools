# 03 Deterministic Rule・固定コンテンツ
提案版：PIRA-R-2.0.0 / PIRA-C-20261018.1。AI呼出し・学習モデル・自由文要約は使用しない。

## 意味状態と処理順
各controlはREPORTED_READY、REPORTED_PARTIAL、REPORTED_NOT_DONE、UNCONFIRMED、AUTHORITY_CONFIRMATION、NOT_APPLICABLE、SKIPPEDのいずれか。すべて回答者の認識であり監査済みFACTではない。
処理順はValidation→Guard→Direct→Relevance→Confirmation→Dependency→重複統合→固定表示順で上限3→固定文と資料選択。
- Guard：不正・矛盾入力ではレポートを生成しない。UNKNOWN/権限外/N/A/SKIPPEDから対策不足・優先テーマを生成しない。
- Direct：選択された事実ではなく「そのように回答した」という認識をそのまま表示する。
- Relevance：業務・情報がテーマに関係することを示す。これ単独では優先テーマを作らない。
- Confirmation：適用可能でPARTIALまたはNOT_DONEの自己申告がある場合だけ次の確認テーマ候補を作る。違反・脆弱性の認定はしない。
- Dependency：同じテーマの根拠を統合し、手順上の前提を先に表示する。新たな対策不足を推定しない。

表示順は実務の整理順を固定したもので、危険度・緊急度・成熟度の順ではない。事故進行中を受け付ける診断ではなく、緊急判定もしない。全テーマを出すために採点することはない。最大3は選択・表示上限。残りはdeferredThemeIdsとして同じ固定順で第3章に「今回の表示上限外」と明示し、隠して「他に確認事項なし」としない。継続時は利用者が選んで別紙を閲覧する案。自動的な購入・相談条件にしない。

## 固定チェックリスト全文（選ばれたものだけ掲載）
各資料は「作業→残すもの」の形式。個人情報の実物提出は求めない。
- K01：対象資料の種類ごとに保管期限と期限後の処理担当を表にする。現在の処理と照合する。法令・契約等で必要な保存期間は担当者に確認してから決める。成果物：種類／期限根拠／担当／処理記録欄の表。
- K02：C04がopenなら、実際の送信前に宛先一覧と送るファイル・共有範囲を照合する手順を一枚にする。B03がopenなら、ダミーデータのテスト送信で宛名差込と配布対象を確認する工程を追記する。成果物：該当工程だけの送信確認票。埋込データの有無も確認対象の例として示し、存在を断定しない。
- K03：退職・異動時に解除すべきアカウントの種類、依頼先、実施確認欄をまとめる。実際のIDやパスワードは診断へ入力しない。成果物：権限変更依頼票。
- K04：外部利用アカウントの種類と多要素認証の利用可否を担当者に確認し、未設定範囲の扱いを決める。成果物：対象／対応可否／確認先／判断欄の表。特定サービス購入を前提にしない。
- K05：業務PCのOS更新担当と更新確認日を一覧にする。未更新と分かった機器について、業務影響を確認して対応日を決める。成果物：更新確認表。本診断だけで未更新端末の存在を断定しない。
- K06：戻す必要のある電子データの種類を選び、担当者と復元確認の方法・日程を決める。原本を壊さない場所で確認結果を残す。成果物：復元確認記録票。既存バックアップや委託先をまず確認する。
- K07：振込先変更を受けたら、依頼文にある連絡先だけで確定せず、以前から確認済みの連絡先で依頼元へ確かめる手順を決める。成果物：変更依頼／確認経路／確認者／承認欄の票。
- K08：誤送信・不審アクセス・紛失を見つけた人が最初に連絡する窓口と、不在時の代行先を一枚にする。成果物：第一連絡先カード。個別の法的報告義務や緊急対応は本診断で判定しない。
- KU：分からない項目と担当外の項目を分け、確認する相手と回答更新日を整理する。成果物：質問ID／未確認・担当外／確認先／確認日欄の表。対策不足の一覧として扱わない。
- K00：今回申告した手順を続けられるよう、担当変更や利用サービス変更時の見直し日を記録する。成果物：継続確認メモ。安全性の認証書ではない。
