# sales-tools デプロイ 運用手順書

関連ドキュメント:

## 前提となる構成

- 本体: Cloud Runサービス `sales-tools`（project: `msp-zabbix`、region: `asia-northeast1`）。本番URL: `https://sales-tools-135863453696.asia-northeast1.run.app`（独自ドメイン未割当。将来割り当てる場合はDNS管理者権限が必要な作業のため別途調整する）
- サービスアカウント: `sales-tools-sa@msp-zabbix.iam.gserviceaccount.com`（`roles/cloudsql.client`をプロジェクトレベルで付与、必要なSecret Managerシークレットへのアクセス権を個別付与）
- コンテナイメージはソースからその都度ビルドされる（`gcloud run deploy --source=.`）。CI/CDパイプラインは無く、開発者のローカル端末から手動デプロイする運用（msp-customer-portalと同じ方針）
- **`Dockerfile`必須**: 本プロジェクトには`Dockerfile`（`msp-customer-portal`と同じ2段ビルド構成、`node:20-alpine`）を用意している。これを削除するとgcloudがCloud Native Buildpacksにフォールバックし、2026-08-23のデプロイ時にBuildpacksが自動選択した`google-24:public-image-next`（プレビュー版ベースイメージ）で`ContainerImageImportFailed`エラーが発生した実績があるため、`Dockerfile`は削除しないこと。
- DB（`sales_tools`、既存Cloud SQLインスタンス`msp-customer-portal-db`内に新規作成したデータベース）へのマイグレーション（`npm run migrate`）は、Cloud Runコンテナ内からではなく、`msp-frontend-server`（GCE VM）にSSHして実行する（同VM上の`cloud-sql-proxy.service`が既に`msp-customer-portal-db`インスタンスへ`127.0.0.1:5432`で中継しているため、`sales_tools`データベースにも追加設定なしで到達できる）
  - `msp-customer-portal`と同様、`sales-tools`をこのVMにgit sparse-checkoutで配置し`npm install`しておく
  - 本番のSecret Managerから生成した`.env`を同ディレクトリに用意する（git管理外）
- 環境変数の管理はmsp-customer-portalと同じく2箇所に分かれる（Cloud Runサービス本体 / `msp-frontend-server`上の`.env`）。新しい必須環境変数（`config.ts`の`required(...)`）を追加した場合は両方に反映すること。

## 手順1: 通常のデプロイ（コード変更のみ、DBマイグレーション無し）

1. コード変更をコミット・push
2. ローカル端末の`sales-tools`ディレクトリで実行する
   ```bash
   gcloud run deploy sales-tools --source=. --region=asia-northeast1 --project=msp-zabbix
   ```
3. 反映確認
   ```bash
   curl -sk -o /dev/null -w 'HTTP %{http_code}\n' https://<sales-toolsのCloud Run URLまたは独自ドメイン>/healthz
   ```
   msp-customer-portalでは`/healthz`（末尾スラッシュ無し）がCloud Run経由で404になる既知の挙動があった。sales-toolsでも同じ現象が起きないか初回デプロイ時に確認し、再現する場合は死活監視も含めて`/healthz/`（末尾スラッシュ付き）に統一すること。

## 手順2: DBマイグレーションを伴うデプロイ（新しいテーブル・列を追加した場合）

1. コード変更（マイグレーションファイル`migrations/*.sql`含む）をコミット・push
2. `msp-frontend-server`にSSHしてマイグレーションを先に適用する
   ```bash
   gcloud compute ssh msp-frontend-server --zone=asia-northeast1-a --tunnel-through-iap
   cd /opt/atlib-msp-dev/sales-tools
   git pull
   npm install   # package.jsonに変更があった場合のみ必要
   npm run migrate
   ```
3. `config.ts`に新しい必須環境変数を追加した場合は、先に手順3（環境変数チェックリスト）を済ませてから`npm run migrate`を実行する
4. マイグレーション成功を確認後、手順1と同様にCloud Runへデプロイする

## 手順3: 新しい必須環境変数を追加した場合の反映チェックリスト

msp-customer-portalの運用手順書と同じ注意点が当てはまる。`src/config.ts`の`loadConfig()`は`required()`で読んでいる値が1つでも欠けているとアプリ全体が起動時に例外で落ちる。新しい必須値を追加したら以下の2箇所両方に反映すること。

1. **Cloud Runサービス本体**
   ```bash
   gcloud run services update sales-tools --region=asia-northeast1 --project=msp-zabbix \
     --update-env-vars=<KEY>=<value>
   ```
   秘匿性の高い値はSecret Manager経由にする（`sales-tools-db-password`等と同じパターン。`src/config.ts`の`resolveSecret()`を参照）。
2. **`msp-frontend-server`上の`sales-tools/.env`**（`npm run migrate`実行時のみ使う）

**注意**: `SLACK_WEBHOOK_DIAGNOSTIC`（`config.slack.webhookDiagnostic`）は`required()`を使っていない任意項目（未設定でもアプリは起動する。Slack通知が送られないだけ）。

**注意**: `ANTHROPIC_API_KEY`（`config.aiAssist.anthropicApiKey`、原価見積ツールのAI提案機能用）も同様に任意項目（未設定でもアプリは起動する。見積詳細画面のAI提案パネルのみ503を返す）。設定する場合はSecret Manager `sales-tools-anthropic-api-key` を作成し、Cloud Runサービスへ`--set-secrets=ANTHROPIC_API_KEY=sales-tools-anthropic-api-key:latest`で注入する。

## 手順4: Anthropic APIキーのローテーション（有効期限30日）

原価見積ツールのAI提案機能が使う`ANTHROPIC_API_KEY`は、Anthropic Console発行のAPIキーで発行から30日で失効する。Anthropic Admin APIはキーの新規発行に対応していない（Console UIでの手動発行のみ）ため全自動化はできない。msp-customer-portal時代はCloud Scheduler `anthropic-api-key-rotation-reminder`による月次Slackリマインドと組み合わせていた（詳細は移設元の[msp-customer-portal/docs/運用手順書_ポータルデプロイ.md旧版の変更履歴](../../msp-customer-portal/docs/運用手順書_ポータルデプロイ.md)を参照）。sales-tools移設後は、このCloud Schedulerジョブの通知先・対象シークレット名を`sales-tools-anthropic-api-key`に向け直す必要がある（**未実施。GCPインフラ作成時に対応すること**）。

1. Anthropic Console（https://console.anthropic.com/settings/keys）にログインし、新しいAPIキーを発行する
2. Secret Managerの既存シークレットに新しいバージョンを追加する
   ```bash
   echo -n "<新しいAPIキー>" | gcloud secrets versions add sales-tools-anthropic-api-key --project=msp-zabbix --data-file=-
   ```
   **注意**: このコマンドは平文キーをシェルに渡す。実行後のターミナル出力を画面共有・スクリーンショットに含めないこと（msp-customer-portal運用時に実際にスクリーンショット経由で漏えいした前例があるため引き続き注意する）。
3. Cloud Runサービスに新しいシークレットバージョンを反映させる（`--update-secrets`は同名キーでも再指定しないと`latest`を再解決した新リビジョンが作られないため、キー自体を変更していなくても必ず実行する）
   ```bash
   gcloud run services update sales-tools --region=asia-northeast1 --project=msp-zabbix \
     --update-secrets=ANTHROPIC_API_KEY=sales-tools-anthropic-api-key:latest
   ```
4. 見積詳細画面のAI提案パネルで実際に提案を取得し、503/502にならず正常に動作することを確認する
5. 動作確認後、Anthropic Consoleで古いキーを失効(Revoke)させる

## 既存データの移行（msp-customer-portalからの初回移行時のみ）

対象テーブル: `isms_diagnostic_submissions`, `market_rates`, `estimate_preconditions`, `estimates`, `estimate_line_items`, `estimate_selected_preconditions`。

1. `msp-customer-portal`のCloud SQLから対象テーブルのみ`pg_dump --table=... --data-only`でエクスポート
2. `sales-tools`の新DB（`sales_tools`）に対し、まず`npm run migrate`でスキーマを作成してからインポート
3. 件数照合（`SELECT COUNT(*)`）で移行漏れがないことを確認
4. 移行確認後、`msp-customer-portal`側で旧テーブルを削除するマイグレーションを追加・適用する

本番データに対する`pg_dump`・旧テーブルの削除は破壊的操作のため、実施前に必ずバックアップの存在を確認し、関係者の合意を得てから行うこと。

**判明した落とし穴（Windows/PowerShellでのSecret Manager操作時の注意）**: `$value | gcloud secrets create ... --data-file=-`のようにPowerShellの**パイプ**で文字列をgcloudの標準入力へ渡すと、PowerShellがパイプライン出力を行単位でシリアライズする際に**末尾へ改行(`\n`)が1文字混入する**。これにより、`DB_PASSWORD`・`ADMIN_BASIC_AUTH_USER`/`ADMIN_BASIC_AUTH_PASSWORD`の初回作成時に実際の値と1バイトずれたシークレットが保存され、DB接続の`password authentication failed`（`EstimateRepo.list`等でアプリが未処理例外によりクラッシュ）、および管理画面Basic Authの401エラーの原因になった（2026-08-23、初回デプロイ直後に発覚・DBパスワードのローテーションと管理者パスワードの再設定で解消）。**回避策**: 値は一度ファイルに`-NoNewline`で書き出し、`gcloud secrets ... --data-file="<ファイルパス>"`のように**ファイルパスを直接指定**する（パイプを使わない）。同様に、`gcloud secrets versions access`の出力をPowerShell変数で受けて後続処理する場合、末尾に空行があると配列として返ってくることがある点にも注意（`-join ""`等で結合してから使うか、単一行なら文字列としてそのまま扱う）。
